## 变更内容

- **MMSP 服务端**（`mmsp.integration.server`、`@prismshadow/mmsp/integration/server`）：通过 HTTP 把一张表里的模型提供为 MMSP 流。每一行的 `model_id`、`api_key` 和 `server_model_id`（调用方使用的 id）必填；`base_url`、`client_type` 为空或不写时交给 `AutoLLMClient` 决定（用它的默认端点；客户端先看 `CLIENT_TYPE`，否则用模型 id 对应的官方客户端）。`api_keys` 列出调用方可以发送的 bearer key，可以有多个；列表为空时服务端对所有请求开放，并在启动时说明。两者都来自同一个 JSON 文件，通过 `--config PATH` 或 `MMSP_SERVER_CONFIG` 指定，由 `load_server_config` / `loadServerConfig` 读取；其中 `base_url`、`api_key`、`client_type` 或 `api_keys` 里以 `$` 开头的值从环境变量读取，变量未设置则启动失败。`create_server_app(models, api_keys)` / `createServerApp({ models, apiKeys })` 接收这些行并返回 Flask / Express 应用；`start_server` / `startServer`（返回 `http.Server`）启动它；`--host`、`--port` 默认 `127.0.0.1:25752`，因此调用方的 base URL 是 `http://127.0.0.1:25752/v1`。每一行的上游客户端在启动时构建一次；表为空、某个必填列缺失、`server_model_id` 重复、某个 key 为空或某行被其客户端拒绝时，启动失败并指明是哪一行或哪个 key。
- `GET /v1/models` 以 OpenAI 的格式列出表中的模型：`{"object": "list", "data": [{"id": <server_model_id>, "object": "model", "created": <unix s>, "owned_by": "mmsp"}, ...]}`。
- `POST /v1/stream` 接收 `{"model", "messages", "config"}`，以 server-sent events 响应：公开流的每个事件一行 `data: <UniEvent JSON>`，最后是 `data: [DONE]`；模型没有输出时每 15 秒写一行 `: keep-alive` 注释。`config` 原样转发，因此 `trace_id` 在服务端也会保存一份。调用方断开时，上游请求随之中止。请求体上限 50 MB。
- 错误格式为 `{"error": {"type", "message", ...}}`：没有带服务端的任一 key 返回 401 `AuthenticationError`，请求体格式错误返回 400 `InvalidRequestError`，模型不在表中或路由不存在返回 404 `NotFoundError`，请求体超限返回 413；流开始之后，错误是一个错误事件，随后是 `data: [DONE]`。
- 字节数据以 base64 传输；只有 `inline_data.*` 和 `inline_thinking.*` 项的 `data` 会解码回字节。
- **`mmsp` 客户端**（`mmsp/`、`MmspClient`），兼容客户端类型 `mmsp`：原样返回服务端的公开流，只把字节数据解码回来，自己不保存追踪（由服务端保存）。`MMSP_API_KEY` 只与 `MMSP_BASE_URL` 一起读取；只传 `base_url` 不传 `api_key` 时不发送 key（开放的服务端）；默认 `http://127.0.0.1:25752/v1`；请求 `{base_url}/stream` 和 `{base_url}/models`。`list_models` 返回表中的 id。
- 服务端报告的任何错误，无论是拒绝请求还是流中的错误事件，`mmsp` 客户端都以新增的 `UpstreamError` 抛出（`client`、`status`、`error_type` / `errorType`、`message`，以及 `error`，即服务端发来的错误对象，带着各自的字段），两个包都导出。
- `mmsp.wire` / `src_ts/src/wire.ts`：服务端与客户端共用的路由、默认值和字节编解码，以及服务端写出的错误编码。
- `resolve_server_config(config, source)` / `resolveServerConfig(config, source)`：`load_server_config` 的结构检查和 `$VAR` 解析，与 Playground 共用。`read_server_config(path)` / `readServerConfig(path)`：按原样返回文件内容，不解析 `$VAR`，保留所有键。
- `announce_server` / `announceServer`：打印启动信息 `Starting MMSP server at <base URL>`、`Serving models: <ids>`，服务端开放时再加一行 `Open server: api_keys is empty, every request is accepted`；`start_server` / `startServer` 和 Playground 都调用它。
- `GET /v1/metrics`（`ServerMetrics`，与其他 `/v1/` 接口一样需要 key）：自启动以来的总计和每个模型的请求数、成功数（以 stop 事件结束）、失败数（以错误结束）、断开数（单独计数）、进行中的请求数、成功率、最近 1000 次成功的首个事件耗时和整体耗时的 p50/p90、token 用量、`tokens_out`（思考 + 回复）、`generation_ms`（从首个事件到结束的耗时之和）和 `tps`（`generation_ms` 内每秒的 `tokens_out`）；到达模型之前被拒绝的请求和 `errors`（最近 100 次失败，最新的在前）只计总数；每个模型还有最近一次请求的时间、结果和错误；`since` 为历史的起点。加上 `?window=N`（10 到 5184000）会多出 `window`，即最近 N 秒，改用 `?from=F&to=T`（unix 秒，相隔不超过 60 天）则是这段时间；`?columns=C`（1 到 1440，默认 360）限定列数上限，列宽 `bucket_s` 取 10 s 到 12 h 中能满足列数的最小值，且不细于范围起点处保存的桶；`start` 和 `end` 按列宽对齐，数组覆盖整个范围；包含总计和每个模型的合计与逐列数据，以及 `previous`，即前一个范围的合计；取其他值返回 400 `InvalidRequestError`。历史分为 2 小时的 10 秒桶、2 天的 1 分钟桶和 60 天的 1 小时桶，桶超出所在粒度的保留时长后并入下一级粒度的桶，延迟样本保留均匀分布的 64 个；请求计入它开始时所在的桶，一个 10 秒桶的分位数取自它的前 64 次成功。`--metrics FILE` / `metrics_path` / `metricsPath` 把历史（桶、错误和 `since`）保存在文件里，启动时读取，有变化时每 60 秒写入一次，停止时再写入；文件是一行 JSON：`version`、`since`、`saved_at`、`errors`、`total` 和 `models`，每个序列按桶的粒度分为若干 `[start, bucket]` 列表；表中已没有的 id，其历史仍留在文件里；文件无法读取时从头记录，并在启动时说明。Playground 的 server 页面把这些数据画出来；404 的提示信息列出了这三个路由。
- Playground：客户端类型选择器中新增 `mmsp`（"MMSP server"），默认 base URL 为 `MMSP_BASE_URL` 或 `http://127.0.0.1:25752/v1`；新增 `/server/` 页面（从顶栏进入），页面上的模型表（Client type 留空为 Auto，Base URL 留空为 Default）、`api_keys`、host 和 port 保存到 `MMSP_SERVER_CONFIG`，未设置时保存到缓存目录下的 `server.json`（命令行的格式外加 `host` 和 `port`，值按输入原样写入），服务端按保存的文件在 Playground 进程内启动（`GET`、`PUT /server/api/config`，含文件的 `text`；`GET /server/api/status`，含正在运行的 `config`；`GET /server/api/metrics`，在进程内读取正在运行的服务端的指标，`?window=N`、`?from=F&to=T` 和 `?columns=C` 与 `/v1/metrics` 相同；没有服务端运行时为 `{"running": false}`，有历史时再加上历史的 `since`、`errors` 和所请求的窗口；`POST /server/api/start`、`/restart`、`/stop`；`$VAR` 形式的值在启动时从 Playground 的环境变量读取）。服务端的指标历史保存在配置文件旁边的 `<config>-metrics.json` 里（`server.json` 旁边就是 `server-metrics.json`），所以 Apply 和重启之后接着记录。页头显示状态和 base URL，下面是三个标签页：Overview、Models（每个模型收起为一行，显示提供的 id、上游和状态，点开即可编辑）和 Settings（key、host、port，以及 File：格式化显示已保存的文件，明文 key 遮住、点开才显示，附文件路径和复制按钮）。每一行、每个 key 和监听地址都标有 Live、Saved 或 Unsaved；Save（也可按 Ctrl/Cmd+S）写入文件；保存过文件后 Start 才可点；Apply（`/restart`）先构建新服务端再停掉旧的。Overview 按最近 15 min、1 h、6 h、24 h、7 d 或 30 d，或自选的 From/To 时间范围（不超过 60 天）显示，服务端运行期间每 3 秒刷新：六个指标卡（Requests、Success、Latency p50、Latency p90、Tokens out、TPS）及其与前一个时间范围相比的变化，每个模型一张卡片（状态、请求数、成功率、p50、p90、TPS、最近一次请求的结果、趋势），点卡片会在 Models 里打开该行，按结果分类的 Requests 图，p50 和 p90 两条线的 Latency 图，以及 Errors 列表；服务端停止时显示一个清单（添加模型、保存、启动），有历史时清单下面显示历史。未保存的草稿留在浏览器的 `mmsp.playground.server` 下；启动和停止都会打印到 Playground 的控制台，Playground 启动时还会打印 tracer 和 server 页面的链接。
- Playground 聊天页面：列出的模型以模型 id、客户端类型和 base URL 三者为一项，并记住最近一次列出时用的 API key；模型 id 相同的项分开列出，描述为 `<client type> · <host>`，选中一项即填入它的客户端类型、base URL 和 key。只换了 key 再次列出时不新增，只更新该项的 key。
- 文档：README 新增 MMSP Server 一节，站点 Tools 下新增 Server 页面（含指标一节），客户端列表加入 `mmsp`，错误页新增经由服务端的错误一节，并更新了 skills 参考文档。
